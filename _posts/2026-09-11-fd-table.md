While I was writing a `keymap` for my shed config the other day, I noticed something that kind of bothered me. I can't remember precisely what I was trying to do with the keymap, but I remember the issue I was facing quite clearly: there was some error state that was reachable, and it was printing the fully formatted error to the terminal every time. I decided to just redirect the command throwing the error to `/dev/null`, as you do, but then realized something. If I wanted to redirect stderr here, I would suddenly be paying for an entire fork just to do that.

## Shells and forking

For anyone unfamiliar, `fork` is the general UNIX method for launching new programs. The program clones itself, and then the function returns a different value in both processes. The newly forked process then calls `execve` to shapeshift into a different program. It's technically marvelous, but it is a *very* heavy operation, and in a lot of cases it is pure overkill for what the `fork` is trying to accomplish.

Take the `cat` command for example. It is probably the single most primitive core utility in the UNIX toolchain. The most common use case for this command is to perform this insanely complex two-step process:
1. Read bytes from some input provider
2. Write the same bytes to some output receiver, completely unchanged

Of course, `cat` has other uses outside of this, but typing `cat <some_file>` accounts for more than 99% of my uses of this command. And in order to perform this mind numbingly simple operation, the shell running the command has to do all of this nonsense:
1. call `fork`, register child in the internal job table
2. in the child process, write all exported variables to `envp`
3. child now calls `execve` to shapeshift into the `cat` binary
4. `cat` now executes like 30 lines of code or something
5. the parent now blocks on `waitpid`, waiting for the child to exit
6. `cat` exits, the kernel now sends `SIGCHLD` to the shell to signal that the child process has exited
7. parent process reaps the now-exited child process and cleans up the job table entry

And this is actually the abbreviated version. All of this work to simply execute `read` and `write` in a loop.

It's my opinion that the shell itself should have absolutely no problem doing this internally. There's just no reason to rely on the presence of an external program for something so primitive. It's like having an image editor that doesn't ship with the paint brush tool, or something.

So anyway, what does all of this have to do with the `2> /dev/null` redirection I mentioned earlier?

## The I/O Stack

A while ago, I implemented "in-process" pipelines and command substitutions for shed. They work by detecting when a command consists of only *pure builtins* that don't affect shell state, and contain zero external command calls. The detection for this is actually quite deep, even traversing command substitutions and function calls.

Anyway, if shed detects one of these in-process-eligible commands, it shifts the execution model for pipelines. Instead of forking a new process per command and wiring real pipe file descriptors to their inputs/outputs, shed instead runs these commands internally and uses a stack of *internal byte sinks* to transfer I/O between commands. The stack model allows for arbitrary nesting of pipelines, so that you can still get zero-fork pipelines even with really weird invocations like
```sh
cmd1 | cmd2 | { cmd3; cmd4 | cmd5; } | cmd6
```

This saves a *ton* of time because we free ourselves from ever having to wait on the kernel to handle anything for us. On builtin-heavy workloads, the performance savings are immense. Take a look at this POSIX implementation of *naive fibonacci recursion*:
```sh
fib() {
  n="$1"
  if [ "$n" -lt 2 ]; then
    echo "$n"
    return
  fi
  a=$(fib $((n - 1)))
  b=$(fib $((n - 2)))
  echo $((a + b))
}
fib 20
```

Here's the `hyperfine` result for `shed`, `bash`, and `zsh` for this same `fib(20)` call:


| Command | Mean [ms] | Min [ms] | Max [ms] | Relative |
|:---|---:|---:|---:|---:|
| `shed` | 375.6 ± 9.3 | 363.5 | 391.5 | 1.00 |
| `bash` | 4723.3 ± 118.2 | 4499.6 | 4885.8 | 12.58 ± 0.44 |
| `zsh` | 4651.9 ± 86.9 | 4541.5 | 4801.7 | 12.39 ± 0.38 |


The vast majority of the ~4.6 seconds `bash` and `zsh` need to complete this are spent doing exactly that ridiculous laundry list of tasks I wrote about in the previous section. This isn't to say `bash` and `zsh` are doing it wrong, their model is demonstrably POSIX compliant by design, and `shed` by comparison has to be very careful not to let state changes leak between pipeline segments since everything runs in-process. `bash` and `zsh` trade speed for safety, predictability, and isolation.

The main issue with `shed`'s I/O stack model though is that it cannot model redirections; if a command has *any* redirections, we must ask the kernel to handle it for us, *and this includes stuff like `2> /dev/null`*, which literally just means "throw away this command's stderr output". We can totally do that ourselves though, so why settle?

## The Virtual File Descriptor Table

Naturally, if we want to reduce the amount of time we spend waiting on the kernel, that means the shell itself is going to have to become *more like the kernel*. So how can we steal more work from the kernel?

Well, let's think about why pipeline stages even need to `fork` in the first place. In order to actually transfer the output of one command to the input of another command, you need to make the `pipe` system call, which gives you two new file descriptors; one of which can be written to and one can be read from. These file descriptors have the same relationship as a microphone and a speaker. The output of the first command is pointed at the "microphone", and the "speaker" is then pointed at the input of the second command. The end result looks something like this:

```
            fork() --- fork() --- fork() --- fork()
             --- pipe() --- pipe() --- pipe() ---
<input> --> cmd1 W─▶─R cmd2 W─▶─R cmd3 W─▶─R cmd4 --> <output>

```

Our in-process system did something similar, but the W and R bits were globally accessible in-memory buffers instead of OS-level file descriptors. We can do better though; what if we *internally modeled the OS-level File Descriptor table* from first principles?

The kernel-managed, per-process file descriptor table is pretty simple conceptually; whenever you open a file, or any file-like resource, the kernel puts it in a slot on the table and tells you the number of the slot it was put in. When you call `write(3, buf)` or similar, what you're really telling the kernel is "take this buffer and write it to the resource in table slot #3".

The big thing to take away from this is that once a resource has been put in the FD table, we no longer care what the resource actually is. The FD table becomes an opaque interface that lets us interact with each resource the exact same way. In Rust, this kind of interface could be trivially modeled as a trait.

## Sinks and the Sink Trait

So the `Sink` trait was born, and with it came the refactor of the `Sinks` table (the I/O stack) to instead hold a hashmap of `RawFd -> Arc<dyn Sink>`. The table is indexed by raw integers and returns a handle to something you can read from and/or write to. Sound familiar? That's basically what OS-level file descriptors *are*, conceptually.

With this change, we can now *arbitrarily create entirely new types of files*, since we now have direct access to the implementation details of what `shed` considers to be a file. For example, we can create an in-process representation of the `/dev/null` character device, which solves the problem that originally sparked this entire redesign!

#### src/procio.rs:1034
```rust
/// Internal `/dev/null` equivalent
///
/// Redirections to `/dev/null` create one of these
pub(crate) struct NullSink {
  devnull_fd: OnceLock<OwnedFd>,
}
impl NullSink {
  pub(crate) fn new() -> Self {
    Self {
      devnull_fd: OnceLock::new(),
    }
  }
}
impl Sink for NullSink {
  fn read(&self, _buf: &mut [u8]) -> io::Result<usize> {
    Ok(0)
  }

  fn write(&self, buf: &[u8]) -> io::Result<usize> {
    // return the buf length to pretend we wrote the whole thing
    Ok(buf.len())
  }

  fn flush(&self) -> io::Result<()> {
    Ok(())
  }

  fn as_os_fd(&self) -> io::Result<BorrowedFd<'_>> {
    match self.devnull_fd.get() {
      None => {
        let devnull = fcntl::open("/dev/null", OFlag::O_RDWR | OFlag::O_CLOEXEC, Mode::empty())?;
        let _ = self.devnull_fd.set(devnull);
        self.as_os_fd()
      }
      Some(fd) => Ok(fd.as_fd()),
    }
  }

  fn kind(&self) -> SinkKind {
    SinkKind::Null
  }

  fn poll(&self, _timeout: Option<PollTimeout>) -> io::Result<usize> {
    Ok(0)
  }
}
```

This `Sink` variant is created whenever a redirection to `/dev/null` occurs. As you can see, the `Sink` trait has a method that materializes the `Sink` as a real OS-level file descriptor, `as_os_fd()`. This is used when we actually need to perform process-level I/O redirection for external command execution, and the call is deferred until it is actually necessary. Otherwise, the `NullSink` remains a completely in-process construct, completely usable by builtins and other internal machinery with *no kernel involvement at all*.

With this design, file descriptor redirection is now handled the same way that the shell handles exported variables; they do not materialize until *after* we have already forked. As a result, the parent shell's `envp` and FD table remain completely clean throughout the lifecycle of the program.

After landing this refactor, there was one more potential payoff hiding in the idea of modeling files as plain Rust objects: because the `Sink` trait is bounded by `Send + Sync`, every `dyn Sink` object can be shared across threads. This means that the stages of shed's internal pipelines could be run *concurrently* rather than sequentially. Landing this implementation would mean that these internal pipelines would mirror external pipelines *exactly*:
* All pipeline stages would run at the same time
* I/O production and consumption would become incremental streams instead of wholesale buffering
* Pipeline stages would get roughly the same level of isolation as a forked child, since state is thread_local
* Builtins would finally get a real representation (the `JoinHandle`) on the job table instead of getting a dummy entry with the shell's pid
* Pipelines with mixed builtins and externals would be able to run truly concurrently (!!!)

It all sounded perfect. And with the addition of the `ThreadSink` variant, this idea could come to fruition. [What could possibly go wrong?](https://km-clay.github.io/2026/09/11/thread-pipelines.html)
